# Gymrez PACE — قرارداد تطبیق دقیق طراحی
وضعیت: قرارداد برنامه‌ریزی؛ استخراج مقادیر دقیق و cropهای native در [T01 / #2](https://github.com/Hamrez95/Gymrez/issues/2) تکمیل می‌شود. رنگ/فونت/فاصله‌های عددی هنوز اندازه‌گیری و تأیید نشده‌اند؛ از حدس به‌عنوان مقدار قطعی استفاده نکن.

## الزام غیرقابل حذف
**کاربر دقیقاً همان موکاپ‌ها را خواسته است؛ مشابه‌سازی، بازطراحی سلیقه‌ای و جایگزینی با UI پیش‌فرض کتابخانه قابل قبول نیست.** هر Issue رابط باید تصویر مرجع، پنل هدف، حالات تکمیلی و شواهد تطبیق داشته باشد.

## آنچه باید از مرجع حفظ شود
زمینه سرمه‌ای تیره، آبی الکتریکی روی CTA/انتخاب، پنل‌های کم‌نور با خطوط باریک، گرافیک‌های // و مورب، لوگوتایپ، تصویرهای ورزشکار با tonality سرد، تیترهای فارسی درشت، عنوان‌های انگلیسی فرعی حرکات، ساختار مشخص navigation و progress سگمنتی. تصویر مرجع مجوز افزودن glassmorphism سنگین، گرادیان بنفش، تایمر دایره‌ای یا صفحه بازطراحی‌شده نیست.

تصاویر شیت‌ها ارائه چندپنلی‌اند؛ border قاب دستگاه، نوار مرورگر/نشانی و عنوان شیت بیرون UI اپ هستند. برای مقایسه فقط پنل داخلی در ابعاد native crop شود. اصل PNGها را تغییر نده. crop/assetهای استخراجی کنار اصل با source map نگهداری شوند. اگر فایل asset اصلی جدا موجود نیست، ابتدا از مرجع استخراج با کیفیت مناسب بررسی شود؛ جایگزین دقیق‌نما بدون اعلام اختلاف، done نیست.

## تکمیل قسمت‌های ناقص
- ورود ایمیل/رمز و بازیابی، onboarding و حالت نبود برنامه.
- فرم‌های طولانی و انتهای جدول‌های خارج کادر؛ create/edit/detail و back.
- loading/skeleton، empty، invalid، offline، pending sync، error/retry، success و destructive confirmation.
- نصب PWA و پیام نسخه جدید، paused backend، conflict و export/restore.
- تم روشن و responsiveهای فاقد مرجع از همان tokens و hierarchy توسعه داده شوند.
- اختلاف متن navigation در شیت‌ها به ساختار ثابت خانه/برنامه و تمرین/پیشرفت و سابقه/پروفایل نگاشت شود؛ تمام صفحه‌ها حداکثر با دو اقدام در دسترس باشند.
- تصویر نمونه دکمه play/QR دارد؛ در محصول مقصد واقعی یا fallback توضیح‌دار داشته باشد، نه کنترل مرده.
- خطای متن تولید تصویر، عدد نمونه یا فرمول نباید به رفتار واقعی منتقل شود. ثبت تصمیم در deviation log الزامی؛ صحت/دسترسی‌پذیری مقدم بر بازتولید خطاست.

## responsive و دسترس‌پذیری
مرجع موبایل و دسکتاپ هر دو اجرا شوند؛ صرفاً کوچک‌کردن نسخه دسکتاپ قبول نیست. viewportهای QA: 360، 390، 430، 768 و 1440؛ ارتفاع و ابعاد native پنل‌ها در T01 مشخص شود. RTL، ارقام فارسی/لاتین، متن انگلیسی bidirectional، صفحه‌کلید گوشی، safe-area، focus و اندازه لمس حداقل 44px کنترل شود. کنتراست WCAG AA؛ اگر مرجع ناخواناست اصلاح حداقلی مستند.

## موشن
جزئیات در [MOTION_SPEC](MOTION_SPEC.md). موشن باید حالت ایستا و hierarchy مرجع را حفظ کند و در همه مسیرهای کلیدی وجود داشته باشد. feedback فوری برای اقدام، حرکت کوتاه برای transition، بدون مزاحمت ثبت ست. کاهش حرکت به‌صورت سراسری رعایت شود.

## پذیرش تصویری
1. fixture مصنوعی ثابت برای حالت مرجع بساز؛ ساعت/اعداد/نمودار/viewport ثابت.
2. screenshot واقعی اپ را کنار crop اصل و overlay بررسی کن؛ baseline خودساخته جای اصل را نگیرد.
3. فاصله، رنگ، فونت، اندازه تصویر، آیکون، border، سایه و جای CTA در گزارش بررسی شود. صرف درصد pixel-diff برای تصویر تولیدی و فونت ضدلبه کافی نیست.
4. اختلاف‌ها: P0 صفحه/ساختار نادرست؛ P1 هندسه/رنگ/تصویر عمده؛ P2 جزئیات کوچک. P0/P1 باز مانع پذیرش است.
5. شواهد در docs/implementation/evidence/<task>/؛ تصاویر واقعی بدن/برنامه خصوصی کاربران در ریپو قرار نگیرند.
6. تمام تفاوت‌های ضروری با ستون‌های «مرجع/بخش/تفاوت/علت/وضعیت» ثبت و در PR گزارش شوند. تغییر زبان طراحی به تصمیم صریح کاربر نیاز دارد؛ تکمیل routine stateها نیازمند توقف برای سؤال نیست.
